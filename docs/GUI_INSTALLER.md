# Графический установщик Skrumi

Пока новый стабильный релиз не опубликован, исполняемые файлы в CI являются
кандидатами для проверки, а не рекомендованной стабильной поставкой.

## Исходники и сборка

Прикладная логика полностью написана на Skrumi:

- `installer/main.skm`: окно, параметры, выбор LSP, прогресс, журнал, диалоги и CLI-режим.
- `installer/transaction.skm`: владение файлами, staging, backup, журнал и восстановление.
- `installer/editors.skm`: обнаружение редакторов, объединение настроек и обратимые изменения файлов.
- `installer/integration.skm`: планирование и откат Windows-регистрации удаления.
- `installer/legacy.skm`: проверяемый импорт манифестов предыдущих установщиков.

`packaging/build_gui_installer.py` только собирает ресурсы и вызывает публичную
команду `skrumi build --resources`. Python не входит в приложение и не нужен
конечному пользователю. C++ содержит общедоступные runtime/OS/UI API.

```sh
python3 packaging/build_gui_installer.py --runtime build/skrumi \
  --lsp build/skrumi-lsp --output Skrumi-linux-x86_64.run
```

Для Windows укажите собранные на Windows `build/Release/skrumi.exe` и
`build/Release/skrumi-lsp.exe`, а выходному файлу дайте расширение `.exe`.
Упаковщик сверяет версии с `VERSION` и отказывает для непроверенных архитектур.
Linux-релиз должен собираться из статических бинарников portable Docker target;
обычная локальная CMake-сборка может зависеть от библиотек своей системы.

Payload содержит CLI `skrumi`, LSP `skrumi-lsp`, единственные `.skm`-реализации
модулей `std`, оригинальный логотип,
шрифт и лицензии, файлы интеграций редакторов (устанавливаются только по выбору). Предварительная установка Skrumi и интернет для установки не нужны.
LSP можно отключить; CLI/runtime и стандартная библиотека обязательны.

Linux использует X11 (Xorg либо XWayland). Установка выполняется без root в
пользовательский каталог. Windows использует Known Folders и HKCU без изменения
системного PATH. Поддерживаемая архитектура текущей упаковки — x86_64.

## Язык интерфейса

Первый экран предлагает **Русский** или **English**. Выбор действует на приветствие,
параметры, список каталогов, кнопки, диалоги, этапы и журнал операций, а также
сообщения установщика при обновлении, удалении и восстановлении. До начала установки
язык можно поменять кнопкой `Язык / Language` на экране приветствия. Средство
обслуживания тоже начинает с выбора языка. Закрытие до выбора подтверждается
двуязычным диалогом.

Каталог переводов находится в `installer/i18n.skm`. Пути, команды, идентификаторы
и сохранённые журналы не переводятся. Подробные диагностические сообщения ОС/runtime
показываются в исходном виде под локализованным пояснением. Headless-режим сохраняет
английские сообщения и не требует интерактивного выбора.

## Установка и обслуживание

В GUI можно изменить каталог, отключить LSP или PATH и восстановить незавершённую
транзакцию. Для найденной установки кнопка `Удалить... / Uninstall...` открывает
отдельный экран удаления с каталогом и описанием последствий. Удаление не является
флажком среди компонентов. Красная кнопка `Удалить` открывает подтверждение; только
повторное явное подтверждение начинает операцию. `Не удалять`, `Отмена`, Escape
и возврат назад не меняют файлы. Средство обслуживания Windows и режим
`--uninstall-gui` открывают тот же экран. Закрытие активной установки вызывает
подтверждение; подтверждённая отмена восстанавливает прежние файлы и интеграции.
Проценты отражают проверку staging и публикацию файлов, а не задержки таймера.

Для автоматизированной проверки доступны режимы:

```text
installer --headless install DIRECTORY [--path] [--no-lsp] [--vscode] [--kate]
installer --headless uninstall DIRECTORY
installer --headless recover DIRECTORY
installer --uninstall-gui DIRECTORY
```

В headless-режиме PATH изменяется только с `--path`; в GUI этот параметр включён
по умолчанию. Проверка `skrumi --version` выполняется до commit. Запуск другой
версии CLI завершается ошибкой и откатом. Повторная установка позволяет добавить
или убрать управляемый LSP, сохраняя неуправляемые файлы.

В списке каталогов выбранный вариант выделяется фоном и оранжевой полосой.
Если вручную введён другой путь, ни один вариант не выделяется. Кнопка восстановления
активна только при наличии каталога незавершённой транзакции для выбранного пути;
неизвестное содержимое такого каталога не удаляется автоматически.

Посторонние файлы, существовавшие до установки, не включаются в манифест владения
и сохраняются при обновлении и удалении, в том числе внутри `std`. Если имя
постороннего файла совпадает с именем файла поставки, установка завершается ошибкой
без перезаписи этого файла.

Linux PATH записывается в поддерживаемый login-профиль (`.profile`, существующий
`.bash_profile`, либо `.zprofile` при Zsh). Изменение применяется, когда
оболочка читает этот профиль; простого открытия нового терминала может быть
недостаточно. Windows — в пользовательский
реестр с уведомлением об изменении окружения. Новая запись имеет приоритет внутри
пользовательского PATH; уже существующая запись не дублируется. Открытая оболочка
не меняется автоматически; Windows system PATH может иметь приоритет над user PATH.
Не поддерживаемые оболочки получают явную ошибку, а не фиктивный успех.

## Windows-регистрация удаления

Полная Windows-поставка включает отдельную standalone-программу обслуживания,
тоже собранную из `main.skm`. Она содержит режим удаления/восстановления без payload
для новой установки. Для каталога `Skrumi` рядом сохраняются
`Skrumi.maintenance.exe` и `Skrumi.maintenance.json`. JSON фиксирует владение и
SHA-256 программы, чтобы последующая установка могла безопасно обновить её.

Программа находится вне каталога runtime: запущенный Windows executable не мешает
удалять CLI и остальные файлы. Она намеренно сохраняется после удаления для
восстановления, как и файл блокировки. Когда установка удалена и незавершённого
журнала нет, пользователь может удалить эти два файла вручную. Это не временные
staging/backup-файлы; неизвестное или изменённое содержимое не удаляется автоматически.

Запись находится в `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall`.
Имя подраздела зависит от нормализованного пути установки. Записываются
DisplayName, DisplayVersion, InstallLocation, Publisher, URLInfoAbout,
UninstallString и QuietUninstallString. Строка запуска экранируется по правилам
Windows argv, без shell. Планы каждой записи находятся в журнале; отмена и ошибка
восстанавливают снимки. Чужое изменение значения останавливает его перезапись,
но не мешает восстановить прежние бинарники. Пустой подраздел реестра может остаться.

## Владение, миграция и гарантии

Новый `.skrumi-install.json` формата 3 содержит версию, файлы/хеши, PATH и регистрацию.
Форматы 1/2 и журналы формата 2 читаются для совместимости. Журнал формата 3 хранится
рядом с установкой в `.skrumi-transaction`, отдельно от публикуемых файлов.

Импортируются прежние `.skrumi-install` вместе с `.skrumi-files.json` (Windows,
включая UTF-8 BOM) или `.skrumi-files.sha256` (Linux). Хеш каждого управляемого файла
проверяется до замены. Изменённые файлы блокируют обновление и сохраняются при
удалении; неизвестные проекты и конфигурации не удаляются. Необычные экранированные
GNU checksum-записи отклоняются с сохранением установки для ручной миграции.
Старые внешние настройки редакторов, launchers и PATH не имеют сохранённого
обратимого снимка: они сохраняются. Новая установка не объявляет их своей собственностью.

Установка **не атомарна целиком**: пофайловые замены имеют промежуточные состояния.
Не запускайте установленный CLI во время обновления. Журнал предшествует публикации;
следующий запуск предлагает восстановление. Пустой служебный каталог без журнала
можно убрать, неизвестные файлы в таком каталоге сохраняются для ручного разбора.
Проверка путей не является защитой от конкурентной подмены каталогов другим процессом.
При конфликте сохраняются journal/backup; успешный откат не обещается вопреки
чужим изменениям. SHA-256 проверяет соответствие вложенному manifest, а не подпись издателя.
Пустые каталоги и файл OS lock после удаления могут остаться.

## Релиз и проверка поставки

`ci.yml` собирает Windows на Windows runner и portable Linux через существующий
musl Docker target. На обеих платформах проверяется самостоятельный установщик,
установка в отдельный каталог, повторная установка, компоненты, CLI/
команды и удаление. Отдельные тесты проверяют транзакции, GUI и восстановление.
`build.yml` повторно использует CI, ждёт Android и benchmarks, затем проверяет
точный состав assets. Внутренний `linux-runtime` используется только для замеров.

Пользовательские assets: `Skrumi-windows-x86_64.exe`, `Skrumi-linux-x86_64.run`,
Android AAR и два демонстрационных APK, VSIX/XML редакторов, `benchmarks.json`.
Android и редакторы сохраняют прежние `skrumi`-алиасы. ZIP/TAR с языком не
публикуются; исторические релизы и source archives GitHub не меняются.

Ручной запуск release workflow с `publish=false` собирает `verified-release`
без тега и публикации. Публикация разрешена только с `master`, для нового номера
из `VERSION` и после успешных зависимых проверок. Страница загрузки проверяет
GitHub API и показывает только существующие GUI assets последнего stable release.

После проверки CLI установка считается завершённой только при успешной durable
записи commit. Ошибка очистки после commit сохраняет рабочую установку, выдаёт
предупреждение и оставляет журнал для повторной очистки. Перед откатом также
сохраняется намерение восстановления: если журнал нельзя записать, резервные
копии остаются до устранения ошибки доступа/места. Неизвестное содержимое staging
не удаляется ни при завершении, ни при восстановлении.

Окно подбирает начальный размер по рабочей области и настройке Xft DPI на Linux;
Windows выполняет системное DPI-масштабирование. Размер можно менять: интерфейс,
шрифт и области нажатия пересчитываются вместе. Минимальная клиентская область
480×348, рекомендуемая 800×580; требуется дополнительное место под рамку окна.
Автоматическое переключение физического DPI при переносе между мониторами не
реализовано; изменение размера окна остаётся доступно.

## Выбор каталога и обнаружение установки

Кнопка `Locations...` открывает компактный список строк под полем пути: каталог данных
приложений, `Skrumi` внутри домашнего каталога и `.local/opt/Skrumi` на Linux либо
`Local AppData/Programs/Skrumi` на Windows. Выбирается отдельный подкаталог Skrumi,
а не домашний каталог целиком. Путь также можно ввести вручную.

Установщик поддерживает одну управляемую установку на пользователя. Каталог
запоминается в `Skrumi/setup-location.json` внутри `os_user_dir("state")`.
Общая блокировка сериализует операции разных экземпляров установщика. Запись
сохраняется до начала транзакции, поэтому следующий запуск обнаруживает также
прерванную установку. Запись без установленного манифеста и области транзакции
считается устаревшей и не запрещает новую установку.

При запуске проверяются сохранённый путь, подготовленные каталоги и PATH
(включая родительские каталоги для старых установок с `bin`). Найденный каталог
используется для обновления автоматически. Установка во второй каталог запрещена
и в GUI, и в headless-режиме: сначала удалите старую установку. При обнаружении
нескольких старых копий удалите лишнюю явной командой `--headless uninstall PATH`.
Неуправляемые portable-копии и произвольные старые каталоги вне PATH невозможно
надёжно обнаружить без сканирования диска. Для старой установки в таком каталоге
укажите её путь вручную; успешное обновление сохранит его для следующих запусков.
Ограничение относится к текущему пользователю, не к чужим профилям ОС.

## Восстановление после ручного удаления папки в Windows

Повторная установка в тот же каталог автоматически восстанавливает
учёт регистрации, если папка была удалена вручную, но рядом сохранились
`Skrumi.maintenance.exe` и `Skrumi.maintenance.json` (имя зависит от выбранного
каталога). Установщик проверяет контрольную сумму служебного EXE и все семь
значений регистрации: название, версию из служебного манифеста, каталог,
издателя, адрес проекта и обе команды удаления. Это работает также с остатками
установки 8.18.0. Очищать PATH или редактировать реестр вручную не требуется.

Восстановление проходит внутри обычной транзакции. При отмене или сбое
возвращаются прежние значения реестра; после успешной переустановки штатное
удаление убирает восстановленную регистрацию. Неизвестные файлы не становятся
собственностью установщика.

Если служебные файлы тоже удалены, их контрольная сумма не совпадает или запись
регистрации изменена/неполна, автоматическое присвоение этой записи запрещено.
Одного названия Skrumi недостаточно для подтверждения принадлежности.

## Выбор редакторов

На экране параметров откройте **Интеграции редакторов…**. Установщик ищет
исполняемые файлы в PATH и стандартных каталогах текущей ОС (Windows/Linux).
Существующий каталог настроек сам по себе не считается установленным редактором.
Первоначально галочки сняты; при обновлении восстанавливается предыдущий выбор.
Кнопка «Найти снова» повторяет обнаружение. Перезапустите редактор после установки.

- **VS Code:** файлы расширения помещаются в стандартный пользовательский каталог
  `.vscode/extensions/skrinvex.skrumi-language-VERSION`. VS Code обнаруживает их
  при сканировании расширений. Установка офлайн, без запуска редактора и без
  редактирования `settings.json`/`extensions.json`. Приватный `installation.json`
  сообщает расширению выбранный каталог CLI/LSP, в том числе нестандартный.
- **Kate:** устанавливаются подсветка и внешние инструменты; секции Skrumi добавляются
  в JSON LSP Client и отладчика, сохраняя другие серверы и профили. При отключённом
  LSP его секция не добавляется. Модули LSP Client, Внешние инструменты и Отладчик
  включаются пользователем в настройках Kate; установщик не меняет список плагинов.

Zed в этом обновлении не включён в установщик; его dev-расширение по-прежнему
устанавливается вручную по [инструкции](../editors/zed/README.md).

Поддерживается обычная пользовательская установка VS Code и Kate. Portable-профили,
нестандартные `--extensions-dir`, VS Code Insiders/VSCodium, Flatpak и удалённые
extension hosts не настраиваются автоматически: используйте инструкции редактора.
Отключение PATH не мешает локальным VS Code/Kate интеграциям: они получают абсолютные
пути.

Изменения файлов VS Code/Kate входят в журнал транзакции v4: отмена и recovery
восстанавливают снимки. При обновлении можно снять галочку и удалить управляемую
интеграцию. Удаление Skrumi тоже удаляет её, восстанавливая исходные файлы Kate;
последующие посторонние изменения JSON сохраняются. Изменённые пользователем файлы
расширения не перезаписываются: обновление отказывает, удаление сохраняет такие файлы.
Уже существующая чужая секция `skrumi` не заменяется. Старые журналы v2/v3 и манифесты
v1–v3 по-прежнему читаются. Пустые созданные каталоги могут остаться после отката.

В headless-режиме выбор задаётся явно флагами `--vscode`, `--kate`,
без проверки наличия редактора (подходит для подготовки окружения). Отсутствие
флагов означает установку без интеграций, в том числе удаление ранее выбранных при
обновлении. Не используйте эти флаги с `uninstall` или `recover`.
