Как устроен язык Skrumi

Что происходит между строчкой print("Привет!"); и словом на экране: как язык читает текст, хранит числа и списки, вызывает функции, ловит ошибки, рисует окно точка за точкой, отвечает браузеру и почему для него есть отладчик.

    Что вообще такое язык программирования

    Процессор понимает только числа и очень простые команды: сложить, сравнить, перейти. Писать так человеку неудобно, поэтому придумали языки, похожие на обычную речь.

    Skrumi — такой язык. Ты пишешь файл hello.skm:

    print("Привет!");

    и запускаешь skrumi hello.skm. Программа skrumi читает текст, понимает его и выполняет. Сама она написана на C++, быстром «взрослом» языке. Получается, что Skrumi живёт внутри программы на C++, примерно как игра внутри игровой приставки.

    Путь программы: четыре шага

    Когда ты читаешь предложение на чужом языке, ты сначала выделяешь слова, потом понимаешь грамматику, потом смысл. skrumi делает то же самое, а потом ещё переводит понятое в короткие простые команды и выполняет их.

    входТекстфайл .skm, просто буквы
    шаг 1Лексеррежет текст на токены-слова
    шаг 2Парсерстроит из слов дерево смысла
    шаг 3Компиляторпереводит дерево в байткод — список простых команд
    шаг 4Виртуальная машинавыполняет команды одну за другой

    Шаг 1. Лексер
    
      
    Лексер (src/core/Lexer.cpp) идёт по тексту буква за буквой и собирает токены: ключевые слова (int, if), имена (x), числа, строки и знаки. Пробелы и комментарии // он выбрасывает. У каждого токена запоминается строка и столбец: когда что-то сломается, ошибка скажет «строка 12».
    
      
    Шаг 2. Парсер
    
      
    Парсер (src/core/Parser.cpp) знает грамматику: что после int идёт имя, потом =, потом выражение и ;. Из токенов он строит дерево, его ещё называют AST. Умножение оказывается глубже сложения, поэтому считается раньше. Так и получается правило «умножение раньше сложения». Если грамматика нарушена, парсер сообщает Syntax Error с номером строки.
    
      
    Шаг 3. Компилятор
    
      
    Компилятор (src/core/Compiler.cpp) обходит дерево один раз и переводит его в байткод — плоский список простых команд: «сложи ячейки 2 и 3 и положи в ячейку 1», «если не меньше — перейди к команде 7», «вызови функцию». Ячейки называются регистрами. У каждого вызова функции свой ряд регистров: сначала её переменные (параметры первыми), потом числа, с которыми она считает, потом место для промежуточных результатов. Каждая функция компилируется при первом вызове, а дальше её байткод просто используется снова.
    
      
    Вот как выглядит функция Фибоначчи. Это настоящий вывод skrumi disasm:
    
      
    int fib(int n) {
    if (n < 2) {
        return n;
    }
    return fib(n - 1) + fib(n - 2);
}
    
      
    fib(): 9 instructions, 6 registers (1 variables)
    r0 = n
    r4 = 2
    r5 = 1
5        0  compare      if not r0 < r4 -> 2
6        1  return       r0
8        2  sub          r2 r0 r5
         3  call         r2 = fib(r2)
         4  sub          r3 r0 r4
         5  call         r3 = fib(r3)
         6  add          r1 r2 r3
         7  return       r1
9        8  return-void
    
      
    Слева номер строки исходника, потом номер команды и сама команда. if превратился в одно сравнение с переходом, а return — в команду, которая сразу отдаёт значение. Номер строки записан у каждой команды: так ошибка узнаёт, на какой строке она случилась.
    
      
    Шаг 4. Виртуальная машина
    
      
    Виртуальная машина (src/core/Vm.cpp) — это один цикл: взять следующую команду, выполнить, взять следующую. Для частых случаев — сложить два целых, сравнить два целых, взять элемент массива по номеру — у неё есть короткий путь в несколько процессорных инструкций. Всё редкое и сложное она передаёт общему коду, тому же, что знает все правила языка.
    
      
    Такой способ называется байткод и регистровая виртуальная машина, так же устроен Lua. До версии 8.3 Skrumi был интерпретатором по дереву: у каждого узла был метод eval — «вычисли себя», и программа выполнялась, обходя дерево. Это самый простой способ, но медленный. На байткоде вызовы функций стали быстрее примерно в полтора-два раза, а тесные циклы — в два. Перед тем как удалить старый обход дерева, сотню программ прогнали обоими способами и сравнили всё до символа: вывод, ошибки со строками и коды возврата.
    

      
    А как делают другие языки
    
      
    Исполнять дерево напрямую просто, но медленно. Узлы дерева разбросаны по памяти, и на каждый узел приходится отдельный вызов функции. Процессор постоянно ждёт данные из памяти. Поэтому языки, для которых важна скорость, после парсера делают ещё один шаг:
    
      
    
        
    
          
    СпособЧто происходит после дереваКто так работает
    
          
            
    Интерпретатор по деревудерево выполняется напрямую, узел за узломBash, ранний Ruby, Skrumi до 8.3, многие встроенные языки
    
            
    Байткод и виртуальная машинадерево переводится в плоский список простых команд, их гоняет быстрый циклSkrumi, Python, Lua, Ruby 1.9+
    
            
    Байткод и JITгорячий байткод на лету переводится в машинный код процессораJavaScript в браузере, Java, C#
    
            
    Компиляциядерево проходит через десятки оптимизаций и превращается в машинный код заранее; интерпретатора при запуске нет вовсеC, C++, Rust, Go
    
              
        
    
      
    
      
    Лексер и парсер у всех одинаковые. Отличается только то, что происходит с деревом дальше. Skrumi теперь проходит тот же путь, что Python и Lua: дерево, байткод, виртуальная машина. Дальше по этой дороге идёт только JIT, а он на порядок сложнее и для такого языка не окупится.

    Типы проверяются. В переменную int x нельзя положить текст, будет Type Error. Безопасные превращения язык делает сам: целое в дробное, число в текст.
    
      
    Коробки и номерки
    
      
    Числа и текст лежат прямо в значении. Числа хранятся как настоящие числа и превращаются в текст, только когда их печатают. Контейнеры (массив, словарь, структура) устроены иначе: они лежат отдельно, как коробка на складе, а значение держит номерок на эту коробку. Коробка помнит, сколько номерков выдано, и исчезает сама, когда их не осталось. Поэтому память вручную освобождать не нужно.
    
      
    Есть одна ловушка: коробки, которые держат номерки друг от друга. Если в массив положить его самого, у него всегда останется номерок — от самого себя, — даже когда программа о нём забыла. Для таких колец есть сборщик циклов. Время от времени он пересчитывает номерки: вычитает те, что коробки держат друг на друга, и смотрит, что осталось. У коробки, на которую есть номерок снаружи — из переменной или из вызова функции, — он остался; всё, до чего можно дойти от таких коробок, живо. Остальное — забытые кольца, их сборщик разбирает. Так же поступает Python.
    
      
    array a = [1, 2, 3];
array b = a;        // b получает номерок на ту же коробку
b[0] = 100;
print(a, b);        // [100, 2, 3] [100, 2, 3]

void reset(array items) {
    items[0] = 0;   // функция тоже получает номерок на ту же коробку
}
reset(a);
print(a);           // [0, 2, 3]

array backup = copy(a);   // новая коробка с тем же содержимым
backup[0] = 5;
print(a, backup);         // [0, 2, 3] [5, 2, 3]
    
      
    Правило одно: присваивание, передача в функцию и возврат из неё выдают ещё один номерок на ту же коробку. Новую коробку с тем же содержимым делает copy().
    
      
    Так же устроены Python, JavaScript и Java, поэтому привычка переносится: там b = a тоже не копирует список. Другие языки выбирают иначе. В C++ копируется и присваивание, и передача в функцию. В Rust у значения один владелец, а остальные его «одалживают». До версии 8.0 Skrumi копировал при присваивании. Это правило пришлось поменять: оно не совпадало ни с одним массовым языком.
    
      
    struct Point {
    int x;
    int y = 0;
}
map skrumi = {name: "Лис", tags: ["рыжий"]};
Point p = Point(3, 4);
print(skrumi.name, skrumi["tags"][0], p.x + p.y);   // Лис рыжий 7

      •

    Как Skrumi находит переменную быстро
    
      
    Искать имя по комнатам при каждом обращении долго: это сравнение строк в нескольких словарях. Поэтому перед первым вызовом функции Skrumi один раз проходит по её дереву и раздаёт всем локальным переменным номера ячеек: параметрам первыми, потом переменным блоков по порядку. У каждого вызова свой ряд ячеек, и total превращается просто в «ячейку номер 3». Глобальные переменные ищутся по имени один раз, дальше команда байткода помнит, где они лежат.
    
      
    Так делают почти все языки: Python, Lua и JavaScript тоже заранее превращают имена локальных переменных в номера. Комнаты при этом никуда не делись. Они определяют, какой номер получит каждое имя, просто решается это заранее, а не во время работы программы.
    
    
    

    
    
      
    Функции, вызов и return
    
      
    int add(int a, int b) {
    return a + b;
}
print(add(2, 3));   // 5
    
      
      
        
    1. Аргументы 2 и 3 считаются в соседние регистры вызывающего кода.
      2. 
        
    2. Команда call выделяет новый ряд регистров и переносит в него аргументы: a = 2, b = 3.
      3. 
        
    3. Виртуальная машина выполняет байткод функции: add r2 r0 r1.
      4. 
        
    4. return r2 сразу отдаёт значение. Ряд регистров функции освобождается, а 5 попадает в регистр, где лежал первый аргумент.
      5. 
      
    
      
    break и continue — просто переходы к нужной команде. Сложнее всего с finally: он должен выполниться, как бы ни закончился try. Компилятор кладёт копию блока finally на каждый выход из try — перед return, break и в конце, — а для ошибок у каждой функции есть таблица: «ошибка в командах с 3 по 9 — переходи к команде 15».
    
      
    До версии 8.3, во времена обхода дерева, return работал иначе: он поднимал флажок «пора выходить», и каждый блок после каждой строки на него смотрел. А ещё раньше return был исключением C++, в восемь раз медленнее флажка. В байткоде никто ничего не опрашивает: return — одна команда.
    
      
    Есть и защита от бесконечной рекурсии: если функция вызывает себя слишком глубоко, программа получит понятную ошибку вместо аварийного падения. Обычные функции выполняются на собственном стеке виртуальной машины с пределом 100 000 уровней. Лямбды, методы и вызовы из встроенных функций используют стек потока: предел зависит от платформы; в браузере дополнительно действует ограничение в 1000 уровней.
    
      
    Функция — тоже значение
    
      
    Функцию можно положить в переменную типа func, передать в другую функцию и вернуть из неё. Короткую функцию без имени — лямбду — пишут прямо на месте: x => x * 2.
    
      
    func make_counter() {
    int count = 0;
    return () => {
        count++;
        return count;
    };
}
func next = make_counter();
next();
print(next());   // 2
    
      
    Здесь есть загадка: make_counter уже закончилась, её ряд регистров освобождён, а лямбда всё ещё помнит count. Секрет в том, что компилятор заранее видит: переменную count читает лямбда. Такую переменную он кладёт не прямо в регистр, а в маленькую коробку, и в регистре лежит только номерок от коробки. Лямбда при создании получает копию номерка — это и есть замыкание. Регистры исчезают, а коробка живёт, пока на неё кто-то ссылается. Остальные переменные, которые лямбды не трогают, остаются в регистрах и ничего не теряют в скорости.
    
    
    

    
    
      
    Ошибки и как их ловить
    
      
    Деление на ноль, индекс за пределами массива, неверный тип — всё это ошибки выполнения. Ошибка летит вверх через блоки и функции. Если её никто не поймал, программа печатает
    
      
    Skrumi: main.skm:12: Runtime Error: Division by zero
    
      
    и завершается. Если по дороге есть try, ошибка ловится:
    
      
    try {
    int r = 10 / 0;
} catch (e) {
    print("не вышло:", e);
} finally {
    print("это выполнится всегда");
}

throw "своя ошибка";   // бросить ошибку самому
    
    
    

    
    
      
    Встроенные функции и библиотека
    
      
    Встроенные функции написаны на C++: print, size, read_file, push, json_decode и ещё около двухсот. Про каждую записаны имя, типы параметров и описание. Перед вызовом язык сам проверяет, подходят ли аргументы, а редактор показывает то же описание в подсказке.
    
      
    Стандартная библиотека — 17 модулей на самом Skrumi в папке std/: string, fs, http, server, graphics, ui, sound и другие. Строка using fs; подключает std/fs.skm с удобными короткими именами. Эти файлы вшиты прямо в программу skrumi, отдельно их устанавливать не нужно.
    
      
    Свои файлы подключаются через include("utils.skm");. Когда интерпретатор встречает include, он читает этот файл, разбирает его тем же лексером и парсером и регистрирует его функции, структуры и глобальные переменные. Каждый файл подключается один раз, даже если его просят из нескольких мест. Проект из нескольких файлов — одна программа: функции из одного файла видны в другом.
    
      
    // utils.skm
int double_it(int n) {
    return n * 2;
}

// main.skm
include("utils.skm");
using string;
print(double_it(21), upper("лиса"));   // 42 ЛИСА

    Графика: как Skrumi рисует окно
    
      
    Это самая «волшебная» часть языка, хотя внутри она очень простая. Видеокарта не используется. Skrumi сам решает, какого цвета каждая точка окна, и отдаёт готовую картинку операционной системе.
    

      
    Цикл кадра
    
      
    Любая графическая программа на Skrumi — это цикл. Один оборот цикла — один кадр, примерно 60 раз в секунду:
    
      
    using graphics;

open_window(320, 200, "Лиса");        // открыть окно 320×200 точек
int x = 0;
while (window_poll()) {               // 1. забрать события: клавиши, мышь, закрытие
    if (key_down("RIGHT")) {
        x += 2;                       // 2. изменить состояние игры
    }
    clear_window(rgb(20, 24, 36));    // 3. залить весь кадр фоном
    draw_circle(x, 100, 12, rgb(255, 140, 0));
    draw_text(10, 10, "Привет", 2, rgb(255, 255, 255));
    present_window();                 // 4. показать готовый кадр
    wait(16);                         // 5. подождать ≈16 мс, это и есть 60 кадров в секунду
}
close_window();
    
      
    Каждый кадр рисуется заново целиком. Кружок не «переезжает» из старого места: в новом кадре его просто рисуют в новом месте, а старый кадр затёрт фоном. Так работают почти все игры.
    

      
    Кадр — это массив чисел
    
      
    Внутри окна лежит Surface, «поверхность»: массив чисел по одному на каждую точку. У окна 320×200 это 64 000 чисел. Каждое число — цвет в виде 0xRRGGBB: сколько красного, зелёного и синего, от 0 до 255. Функция rgb(255, 140, 0) просто собирает такое число. Координаты начинаются в левом верхнем углу: x растёт вправо, y — вниз.
    
      
    Вот маленький кадр 64×40 точек, увеличенный в 7 раз. Нажимай команды по очереди и смотри, как каждая закрашивает точки. Наведи мышь на кадр, и увидишь координаты точки, как их вернули бы mouse_x() и mouse_y().

    Как рисуются фигуры
    
      
      
        
    • Прямоугольник — самое простое: для каждой строки от верха до низа закрасить точки от левого края до правого.
      • 
        
    • Круг рисуется тоже по строкам. Для строки на расстоянии dy от центра половина ширины круга равна √(r² − dy²) — это теорема Пифагора. Остаётся закрасить отрезок этой строки.
      • 
        
    • Линия идёт по алгоритму Брезенхэма: шагаем по точкам от начала к концу и на каждом шаге решаем, сдвинуться ли ещё и по второй оси. Всё делается в целых числах, без дробей.
      • 
        
    • Отсечение. Всё, что выходит за край окна, не рисуется. Функция clip_begin добавляет свой прямоугольник-рамку: так прокручиваемый список не залезает на соседние элементы.
      • 
      
    

      
    Шрифт из единичек и ноликов
    
      
    Никаких файлов шрифтов Skrumi не использует. Каждая буква — это 7 строк по 5 точек, а каждая строка хранится одним числом, у которого биты означают «точка есть» или «точки нет». Буква A записана в исходниках так: {14, 17, 17, 31, 17, 17, 17}.
    
      
    
        
    
        
    
          
    14 в двоичном виде — 01110: три точки в середине, верх буквы. 17 — 10001: две боковые палки. 31 — 11111: перекладина.
    
          
    Строчные g p q y j д ц щ имеют ещё две строки ниже для хвостиков. Русские буквы, похожие на латинские (А, В, Е, О, Р, С…), используют одни и те же точки. Буква с масштабом 2 рисуется квадратиками 2×2.
    
        
    
      
    

      
    Картинки PNG
    
      
    PNG-файл хранит картинку в сжатом виде, как архив. Функция load_image делает то же, что любая программа просмотра:
    
      
      
        
    1. Читает файл и находит в нём куски: размер картинки, палитру, прозрачность, сжатые данные.
      2. 
        
    2. Распаковывает данные алгоритмом DEFLATE, тем же, что в ZIP-архивах. Распаковщик в Skrumi написан свой, внешних библиотек нет.
      3. 
        
    3. Снимает фильтры строк. Чтобы картинка лучше сжималась, PNG хранит не сами цвета, а разницу с соседней точкой слева или сверху. Эту разницу надо сложить обратно.
      4. 
        
    4. Превращает всё в точки с прозрачностью. Картинка готова к рисованию.
      5. 
      
    
      
    При рисовании полупрозрачная точка смешивается с тем, что уже нарисовано: новый цвет = старый × (1 − α) + цвет картинки × α, где α — непрозрачность от 0 до 1. Так тень или стекло пропускают фон.
    

      
    Окно, клавиатура и мышь
    
      
    С операционной системой Skrumi разговаривает напрямую: на Linux через протокол X11 (он работает и под Wayland), на Windows через Win32, на Android через SkrumiView/JNI. Когда ты жмёшь клавишу или двигаешь мышь, система кладёт в очередь окна событие. window_poll() в начале кадра разбирает всю очередь и запоминает состояние:
    
      
      
        
    • key_down("A") — клавиша сейчас зажата, пригодно для движения;
      • 
        
    • key_pressed("A") — клавишу нажали именно в этом кадре, пригодно для прыжка или выстрела;
      • 
        
    • text_input() — набранные буквы с учётом раскладки, в том числе русской;
      • 
        
    • mouse_x(), mouse_y(), mouse_wheel() — где мышь и сколько повернули колесо.
      • 
      
    
      
    present_window() отправляет массив точек в окно. Нативное окно по умолчанию изменяется мышью; set_window_resizable(false) запрещает это. При расширении сохраняются старые пиксели, а window_resized() подсказывает, что пора заново расставить элементы по window_width() и window_height(). set_window_fullscreen(true) включает fullscreen на Windows/X11, false возвращает размер и положение обычного окна.
    
      
    Сборка skrumi build game.skm --no-console создаёт Windows EXE без терминала. При запуске --skrumi-console / --skrumi-no-console переопределяют режим; --skrumi-width, --skrumi-height, --skrumi-fullscreen, --skrumi-windowed задают начальное окно. Собственные флаги программы доступны через os_args(). Все параметры запуска.
    

      
    Интерфейс без объектов
    
      
    В модуле ui нет объектов «кнопка», которые где-то хранятся. Кнопка существует ровно тогда, когда ты её рисуешь. Такой подход называется immediate mode, «немедленный режим».
    
      
      
        
    1. Каждый кадр ui_button("save", x, y, w, h, "Сохранить") сообщает: «кнопка save сейчас здесь, на таком-то слое».
      2. 
        
    2. В начале следующего кадра система смотрит, какой из записанных прямоугольников под мышью, и выбирает самый верхний.
      3. 
        
    3. Если по нему щёлкнули, ui_button возвращает true. Один щелчок достаётся только одному элементу.
      4. 
        
    4. Модальное окно — отдельный слой, который выключает все слои под собой. Поэтому клик сквозь диалог не проходит.
      5. 
        
    5. Поле ввода с фокусом забирает себе клавиатуру: пока ты печатаешь, ui_typing() истинно, и горячие клавиши программы молчат.
      6. 
      
    

      
    Звук
    
      
    Модуль sound проигрывает WAV-файлы и тоны, не останавливая программу. Тон Skrumi строит сам: считает 44 100 значений синусоиды на каждую секунду звука, плавно поднимает и опускает громкость в начале и в конце, чтобы не было щелчка, и отдаёт звук системе: на Windows через PlaySound, на Linux через проигрыватель рабочего стола, на Android через MediaPlayer.
    
      
    using sound;
beep(440, 200);                  // «ля» первой октавы, 0.2 секунды
play_sound("sounds/jump.wav");
    
    
    

    
    
      
    Веб-сервер и JSON
    
      
    На Skrumi можно написать сайт или API. Сервер встроен прямо в skrumi:
    
      
    using server;

void hello() {
    respond_text("Привет, " + param("name") + "!");
}

route("GET", "/hello/:name", "hello");
static_files("/", "public");     // файлы сайта из папки public
listen(8080);                    // ждать запросов на порту 8080
    
      
      
        
    1. route записывает правило: запрос GET /hello/… обрабатывает функция hello.
      2. 
        
    2. listen открывает сетевой порт и ждёт. Браузер присылает запрос — текст вида GET /hello/Лис HTTP/1.1.
      3. 
        
    3. Сервер разбирает запрос, находит подходящий маршрут и кладёт :name в параметры.
      4. 
        
    4. Вызывается функция hello. Она читает param("name") и отвечает через respond_text.
      5. 
        
    5. Если в функции случилась ошибка, браузер получает ответ 500, а сервер работает дальше.
      6. 
      
    
      
    JSON — формат, в котором сайты и программы обмениваются данными. json_decode превращает его текст в словари и массивы Skrumi, json_value — обратно:
    
      
    map user = json_decode("{\"name\": \"Лис\", \"tags\": [\"рыжий\"]}");
print(user.name, user["tags"][0]);         // Лис рыжий
print(json_value({"ok": true, "n": 3}));   // {"ok":true,"n":3}

    Проверка без запуска
    
      
    Лексер и парсер строят дерево, а анализатор (SemanticAnalyzer.cpp) обходит его, ничего не выполняя. Он проверяет, объявлены ли имена, правильное ли число аргументов и существуют ли типы. Это и есть skrumi check.
    
      
    Помощник в редакторе
    
      
    VS Code, Kate и Zed разговаривают с skrumi-lsp по стандартному протоколу LSP. На каждое изменение в файле сервер заново прогоняет анализатор и отвечает: где подчеркнуть ошибку, что подсказать при вводе, где объявлена функция, как переименовать имя во всех файлах.
    
      
    Отладчик
    
      
    Когда отладчик подключён, Skrumi компилирует функции в особый вариант байткода: перед каждой строкой стоит команда statement, которая спрашивает отладчика «остановиться?». Если на строке точка останова, программа замирает, а редактор по протоколу DAP смотрит переменные, стек вызовов и вычисляет выражения. Регистры функции при этом видны отладчику как её переменные. Без отладчика таких команд в байткоде нет вовсе, и за отладку ничего не платится.
    
      
    Отдельное приложение
    
      
    skrumi build берёт копию самого skrumi и дописывает в её конец твои исходники. Запущенная программа видит «у меня в хвосте есть код» и выполняет его. Поэтому готовому приложению не нужен установленный Skrumi.
    
    
    

    
    
      
    Песочница: Skrumi прямо в браузере
    
      
    В песочнице программу можно написать и запустить, ничего не устанавливая, даже на телефоне. И это не имитация и не сервер, который выполняет код где-то у себя: в браузере работает тот же самый skrumi, что и на компьютере.
    
      
    Тот же C++, только в WebAssembly
    
      
    Компилятор Emscripten собирает исходники Skrumi не в программу для Linux или Windows, а в WebAssembly: это байткод, который браузер выполняет почти со скоростью обычной программы. Лексер, парсер, компилятор, виртуальная машина и встроенные функции те же, строчка в строчку. Поэтому программа ведёт себя в песочнице так же, как на компьютере: те же ошибки с номерами строк и тот же вывод.
    
      
    Сборок две. Обычная (skrumi.wasm) запускает все программы без окна. Программа с using graphics получает сборку skrumi-graphics.wasm, где работает Asyncify: он умеет приостановить программу посреди window_poll(), отдать ход браузеру и продолжить с того же места. Так окно успевает обновиться, а нажатия успевают дойти до программы. Эта сборка примерно вдвое медленнее, поэтому грузится только тогда, когда нужна.
    
      
    Программа живёт в отдельном потоке
    
      
    Страница никогда не выполняет программу сама. Код уходит в web worker, отдельный поток браузера со своей копией Skrumi. Даже бесконечный цикл не замораживает страницу: кнопки, редактор и прокрутка работают.
    
      
      
        
    • Запас. Пока ты пишешь код, следующий worker уже загружен и ждёт. Нажал «Запустить», и программа стартует сразу, без загрузки.
      • 
        
    • Остановка. Worker нельзя вежливо попросить остановиться посреди цикла, поэтому страница его просто завершает и берёт запасной. Так работают кнопка «Стоп» и ограничение по времени.
      • 
        
    • Проверка на лету. Ещё один worker читает код, пока ты печатаешь, и находит ошибки, ничего не запуская: строка с ошибкой отмечается на полях редактора, файл отмечается на своей вкладке, а под редактором появляется список с объяснением. Это тот же анализатор, что у skrumi check и помощника в редакторе.
      • 
      
    
      
    Ограничения, чтобы вкладка не повисла
    
      
    
        
    
          
    ЧтоСколько
    
          
            
    Время работы10 секунд. Программа с окном работает сколько угодно, если окно обновляется: иначе 10 секунд без window_poll()
    
            
    Выводмиллион символов
    
            
    Память512 МБ
    
            
    Рекурсияфункции до 100 000 уровней, как на компьютере; лямбды и методы до 1000, стек браузера меньше
    
            
    Нет совсемсети (HTTP), звука и запуска других программ: такие функции сообщают об этом ошибкой
    
              
        
    
      
    
      
    Файлы, ввод и окно
    
      
      
        
    • Несколько файлов. Каждая вкладка над редактором хранит отдельный файл проекта. Перед запуском они записываются в файловую систему в памяти, в папку /project. Запускается main.skm, остальные подключаются через using и include, как на компьютере. Файлы, которые создаёт программа, живут до конца запуска.
      • 
        
    • Ввод. input() читает строки из поля «Ввод программы», а в выводе видно, что именно было прочитано.
      • 
        
    • Окно. Программа рисует кадр в памяти, как и на компьютере, а worker переносит пиксели на холст страницы через OffscreenCanvas. Клавиши, мышь и колёсико страница передаёт в Skrumi теми же кодами, что и настоящее окно.
      • 
        
    • Телефон. Касание работает как мышь. Для игр есть экранный джойстик со стрелками и пробелом, а для текста есть кнопка, которая открывает клавиатуру телефона.
      • 
      
    
      
    Ссылка на программу
    
      
    Код сохраняется в браузере сам, так что после перезагрузки страницы он на месте. Кнопка «Поделиться» упаковывает все файлы проекта в ссылку: текст сжимается (deflate) и записывается после # в адресе. Эта часть адреса не уходит на сервер, поэтому программа нигде не хранится: она целиком лежит в самой ссылке.

    Собрать интерфейс мышью
    
      
    Skrumi UI — визуальный конструктор окон. Добавляй подписи, кнопки, поля ввода, флажки и панели, двигай их по макету, меняй размеры и свойства. Шаблоны помогают начать, а история действий позволяет отменять изменения.
    
      
    Макеты ПК и телефона задаются отдельно. Сгенерированный код каждый кадр выбирает их по ширине окна и учитывает привязки к краям: например, поле растягивается, а кнопка остаётся справа внизу. Это обычный код graphics и ui, который можно дописать и собрать в executable.
    
      
    Во вкладке «Запуск» работает тот же WebAssembly-runtime, что в песочнице: можно вводить текст и нажимать кнопки. Редактор макета схематичен; точный вид проверяется реальным запуском. Проект хранится локально и переносится через JSON, готовый код скачивается двумя файлами: layout.skm для макета и main.skm для логики. Во вкладке «Код» можно редактировать main.skm: изменение макета не стирает обработчики. Оба файла передаются в предпросмотр и песочницу.

    Android: библиотека и своё APK
    
      
    На Android 9 и новее Skrumi можно встроить в приложение на Kotlin/Java через AAR или упаковать проект .skm в APK. Работает тот же C++ runtime: стандартные модули, файлы, сеть, графика и звук.
    
      
    SkrumiView показывает окно программы внутри Activity. Касания управляют мышью, экранная клавиатура передаёт Unicode, размер холста подстраивается под экран и поворот. SkrumiControls добавляет стрелки, пробел и кнопку клавиатуры. Макеты из конструктора используют тот же API.
    
      
    python3 packaging/build_android.py main.skm --name "Моя программа" -o app.apk
    
      
    Для сборки нужны JDK, Android SDK и NDK. Обычный APK подписан отладочным ключом; релиз подписывается вашим ключом. SDK исполняет программы на рабочем потоке, а Activity управляет запуском, отменой и освобождением ресурсов. Файлы и системные операции подчиняются разрешениям Android.
    
      
    Все экземпляры SDK используют общий рабочий поток: долгая программа задерживает запуск другой до завершения или отмены. На Android 9/15 CI проверяет исполнение на эмуляторах x86_64; для всех четырёх ABI проверяются сборка и структура библиотек.
    
      
    Попробуйте Android APK с лабиринтом в псевдо-3D: это тот же raycaster.skm, с экранными кнопками и полноэкранным режимом. Замеры передачи и вывода кадров выполняются отдельно от VM и сохраняются вместе с моделью устройства.

    Насколько Skrumi быстрый
    
      
    Тесты отвечают на вопрос «работает ли». Для вопроса «насколько быстро» есть бенчмарки — небольшие программы, которые делают одну типичную работу много раз, а мы засекаем время. Они лежат в папке benchmarks/, и каждая написана пять раз: на Skrumi, Python, Lua, Ruby и JavaScript.
    
      
    
        
    
          
    БенчмаркЧто делает
    
          
        
    
      
    
      
    Каждая программа в конце печатает контрольное число, например сумму. У всех языков оно обязано совпасть. Так ни один язык не выиграет за счёт того, что сделал меньше работы. Каждую программу запускают несколько раз, по очереди с остальными, и берут лучший результат (число запусков указано над графиками): остальные запуски больше говорят о загруженности машины, чем о языке.
    

      
    Проверка перед релизом
    
      
    Когда собирается новый релиз, GitHub скачивает предыдущий и запускает обе версии на одной и той же машине. Если новая версия хоть на одном бенчмарке медленнее старой больше чем на 10% (и больше чем на 0,03 секунды, чтобы не реагировать на случайный шум), релиз не выходит. Результаты прикладываются к релизу файлом benchmarks.json, и эта страница берёт числа оттуда.
    
      
    python3 benchmarks/run.py                       # Skrumi и другие языки
python3 benchmarks/run.py --baseline old/skrumi # сравнить с другой версией
    
      
    Бенчмарки сразу окупились. В первый же запуск они нашли две проблемы, которых не видел ни один тест. Словарь искал ключ, перебирая все ключи подряд: 200 000 ключей обрабатывались больше четырёх минут, сейчас меньше секунды. А каждый вызов функции с верхнего уровня программы заново спрашивал у системы размер стека, и это чтение файла стоило в 60 раз дороже самого вызова.
    

      
    Skrumi и другие языки
    
      
    
      
    
      
    
      
    
        
    Честно о том, что видно на графике. Skrumi, как Python и Lua, выполняет байткод на виртуальной машине. Результаты относятся к версиям и машине, указанным над графиками; номер измеренной версии может отличаться от версии сайта, пока новый релиз ещё собирается. Если свежий файл результатов недоступен, показан встроенный архивный замер с собственной датой и версиями. JavaScript в Node.js превращает горячий код в машинный прямо во время работы (об этом было в таблице выше), поэтому в тесных циклах он впереди. Разница в несколько процентов лежит в пределах шума, а на другой машине числа будут другими, так что сравнение служит ориентиром, а не соревнованием.

    Одна программа от начала до конца
    
      
    int square(int n) {
    return n * n;
}
print(square(4));
    
      
      
        
    1. skrumi читает файл целиком.
      2. 
        
    2. Лексер выдаёт токены: int square ( int n ) { return n * n ; } print …
      3. 
        
    3. Парсер строит дерево из двух частей: «объявление функции square» и «вызов print с аргументом square(4)».
      4. 
        
    4. Компилятор переводит верхний уровень программы в байткод: «объявить функцию square», «положить 4 в регистр, вызвать square, вызвать print».
      5. 
        
    5. Виртуальная машина выполняет эти команды. Первая запоминает функцию square.
      6. 
        
    6. Команда call square видит, что байткода у функции ещё нет, и компилирует её тело: mul r1 r0 r0, return r1.
      7. 
        
    7. Для вызова выделяется ряд регистров с n = 4 в регистре r0, умножение даёт 16, return отдаёт его.
      8. 
        
    8. print выводит 16, программа завершается с кодом 0 — «всё хорошо».

    Если совсем коротко
    
      
    Skrumi — программа на C++, которая режет твой текст на слова, строит из слов дерево смысла, переводит дерево в байткод — список простых команд — и выполняет эти команды в своей виртуальной машине. Вокруг этого ядра построены стандартная библиотека, графика, веб-сервер, проверка ошибок, помощник для редакторов, отладчик, тесты и автоматические релизы.
